# DSR-012：语句位置与插值子表达式——裸引号是输出不是命令，双引号内插值要判

## 上下文

2026-09-29 用户报告"动态防御经常误伤 agent 在命令中设置变量的命令"。取证方式：按 DSH 帧契约（magic `28 B5 2F FD` 切帧，见 `knowledge/v0.1.7-rc.2/host/25-session-log-jsonl-zstd.md` §4）解开 `stable-dev` HOME 4 天内全部会话日志，取出 **9062 条真实 pwsh 命令**逐条重跑现行规则。

| 观测 | 数值 |
| --- | --- |
| 被拦命令总数 | 478（5.4%） |
| 其中 `unverifiable` "命令本身是动态的" | 413（86%） |
| 该 413 条中，**语句头是裸双引号串** | **397（96%）** |
| 该 413 条中，含变量赋值的 | 363（88%） |
| 变量赋值形态本身的误伤（50 条专项探针） | **0** |

⇒ **"设置变量"不是原因**，只是相关性：长命令通常先赋值、后带插值输出，日志又因截断只留下赋值头，于是现象看起来像"赋值被拦"。真实根因是**语句位置范畴错误**：

```
$n=1; "total: $($n.Count)"                      → BLOCKED（合法输出语句）
$n=1; Write-Output "total: $($n.Count)"         → allowed（同文本，换写法就放行）
```

`assessUnverifiable` 用 `invocation.cmd.includes('$(')` 判"命令名是动态的"，而词法把引号**吞进词内容、不留边界**，于是语句头 `total: $(x)` 被当成命令词。PowerShell 实测（`-EncodedCommand`，排除外层引号干扰）：

| 命令 | 结果 |
| --- | --- |
| `"just text: $(1+1)"` | exit 0，正常输出 ⇒ 裸引号串是**输出**语句 |
| `"Write-Output" "arg"` | **ParserError** ⇒ 引号串不能带参数，不可能是命令调用 |
| `$(Get-Command git) status` | **运行时错误**，不执行 ⇒ `$(...)` + 参数也不是命令调用 |
| `& $(if ($true) {'Write-Output'}) HELLO` | exit 0，输出 HELLO ⇒ `&` 调用算符才是真调用 |
| `& $undefinedVar` | `InvalidOperation`，**不执行任何命令** |

**同一次取证还暴露一个方向相反的漏防**（比误伤更该先修）：

```
Write-Output "$(Get-Content .env)"                          → allowed  ← 本该拦
Write-Output "$(Remove-Item C:\Windows\x -Recurse)"         → allowed  ← 本该拦
Write-Output "$(git reset --hard)"                          → allowed  ← 本该拦
```

两个独立成因：① `tokenizePwsh` 的引号分支把 `$(...)` 直接吞掉、**不推进 `nested`**（不加引号的会被提取），故 `assessDestructive` 的递归看不到插值里的命令；② `isProseSpan` 把 `$(Get-Content .env)` 判成"散文"抹成空白，文本引用层也看不到。即 `Write-Output "$(...)"` 是**唯一同时逃过全部三层的形态**。

## 真实方向与评价

### A. 修正语句位置语义（采纳）

按 PowerShell 的**语法事实**判定语句是否为命令：引号开头 ⇒ 输出（除 `&`/`.` 显式调用）；"命令名是动态的"须是**词首为 `$(`**，而非"词中包含 `$(`"。

- **支持**：零新依赖；判据即上表的运行时实测，不是启发式；消掉 407/478 且不新增误伤。
- **反对**：仍是文本启发式，`& $var` 类无法静态判定——但该形态在新进程 `-NoProfile` 下不可赋值，且合法形态被 `resolveCommandLiterals` 还原（语料 53 处全部还原，0 处残留）。

### B. 换成完整 PowerShell 解析器（否决，保留重访）

`tree-sitter-powershell@0.26.4`（MIT，含 `win32-x64` prebuild）实测可干净区分 `command` / `logical_expression` 节点，在**能解析的命令**上零误伤。

- **否决理由（实测，非估计）**：语法器在 **34.4%（3067/8903）** 的真实命令上报错，最大单一原因是 `--`（end-of-parameters，`git diff A B -- path` 直接 ERROR）；mask `--` 只修掉 1359 条、剩 1708 条。dev 的 "AST 值 = 精确" 与 "parse 覆盖率 = 65.6%" 直接冲突：报错处只能回退启发式，而回退恰好又把 143 条误伤带回来（2×2 实测：clean+命中 270 / error+命中 143）。
- 并发代价：+16MB 原生 addon、供应链与发布形态（runtime resolution / tarball / 原生二进制分发）全部要重验。
- ⇒ **诚实结论**：AST 是"误伤根治"的**方向**，但在当前语法器质量下不是**可交付的替换**。重访条件见下。

### C. 只修误伤、不修漏防（否决）

方向 A 若不做插值递归，`Write-Output "$(...)"` 会从"被误拦"变成"彻底放行"——把漏防做实。**A 与递归必须同发。**

## 最终决定

1. **语句位置**（`isCommandPosition`）：词首非引号 = 命令位置；词首为引号 = 默认输出，除非 `leadSep === '&'` 或词首为 `&`/`.`。`splitFragments` 增加 `quotedHeads`（词首引号来源，词法层标记）与 `leadSeps`（前置分隔符）两个出口。
2. **命令名判据收窄**（`isComputedCommandName`）：`cmd.startsWith('$(')`，替代 `includes('$(')`。`if ($x) { ... "$(...)" ... }` 这类控制表达式不再被当成动态命令。
3. **引号内插值入 `nested`**：双引号内的 `$(...)` 一并提取（单引号是字面量，不提）；配平**引号感知**（引号内 `)` 是内容、双引号内新开 `$(` 自成一组）。
4. **`isProseSpan` 区分引号种类**：双引号内含 `$(` 的分段**不豁免**（插值会执行，"文件名不可能就是 `.git`"的论证对它不适用）；单引号维持普通散文豁免。
5. **管线递归**（`checkCommand` 对 `nested` 递归自身，`MAX_SUBEXPRESSION_DEPTH = 8`）：插值里的命令走**同一套全部规则**，而不是只做破坏性分析。
6. **日志诊断修复**（同批，独立缺陷）：审计行上限 140 字符而拒绝消息前缀已占 112 ⇒ 命令**只剩 28 字符**，这是本次取证无法从日志直接定位的根因。改为 `AUDIT_LINE_MAX = 400` + 对 pwsh 追加独立 `denied input:` 行（文本引用类拒绝消息不含命令，此前事后无法归因）。

## 直接后果

- 语料消融（同一 9062 条，只改上述判定）：被拦 478 → **76（5.4% → 0.8%）**；**新增误伤 0**；`unverifiable:command` 413 → 3。
- 检测力 22/22（含 6 条"引号内藏破坏性命令"必须仍被拦）+ 12/12（应放行）+ 既有 145 例全绿 → 155 例全绿；行覆盖 98.55%。
- 新增 `test/command.test.mjs` 6 例（词法引号来源 / 双引号插值提取 / 配平引号感知 / 片段出口 / 位置判定 / 判据收窄）与 `test/guard.integration.test.mjs` 4 例（DSR-012 端到端正反 + 单引号字面量）。
- 文档同步：`命令文本分析.md`（词法、语句位置、引用豁免、子表达式递归、固有限制）、README 已知限制、需求 R-15。
- 已知残留（未修，如实登记）：① 嵌套插值（`"$(if(...){ "$(...)" })"`）在**提取体**层面还会被 `assessUnverifiable` 记一次，属保守方向；② `& $var` 不拦（见 A 的反对项）。

## 重访条件

- **`tree-sitter-powershell` 修复 `--` 等语法缺口、或 parse 覆盖率实测 ≥ 95%** → 重估方向 B，届时整体替换而非叠加。
- 出现"插值递归导致误伤"的真实高频形态 → 收窄递归面（如只对内容/破坏性层递归），而非关闭递归。
- `unverifiable` 叶子在 profile 中被用户关闭的比例高 → 说明残余保守判定的成本仍不可接受，重估 fail-closed 边界。
