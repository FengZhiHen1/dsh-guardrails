# DSR-015 — 审批式敏感读与职责收缩（V2 / 0.2.0-rc.2 适配）

- 日期：2026-10-16
- 状态：已实施（代码与测试落地；实例级实测待授权）
- 上游设计依据：`references/dsh-guardrails/已确认设计基线-2026-10-16.md`（用户六轮研讨确认的决定 B / B-2 / C / A / T-A；本文只把其中已确认部分落成实现，不回填未决定项）

## 背景

v1 的 `dsh-guardrails` 是 `ctx.tools.guard` 同步硬拒绝：五类规则（env/git/credentials/system/destructive + unverifiable）+ 一整套 PowerShell 词法/字面量重建/破坏性八子族静态分析。用户随后确认了新的职责分工：

- **B**：敏感文件在明确授权后可读取（废弃「永不可读」模型）；
- **B-2**：高敏感直读使用 DSH 原生一次性审批（`ask` / `ctx.approval`），不另造审批系统；
- **C + A**：`.env` 只有用户在 Profile 插件设置中显式标记才触发额外审批；标记不进项目仓库、不读文件内容探测；
- **T-A**：所有原生 `ask` 的统一等待超时属 **DSH Approval Service / Host answerer 公共边界**，guardrails 不在其内计时。

## 决定

1. **删除 `ctx.tools.guard` 钩子**：guard 是单调拒绝、无审批通道（用户批准也无法越过），必须整体退役才能实现授权读取语义。0.2.0-rc.2 源码核实其语义未变（`packages/core/tools/src/index.ts:1519`，仅 allow 后运行）。
2. **改用 `tools/pre-execute` 返回 `{ kind: 'ask' }`**：普通（append）注册，与 Auto Review（`{ prepend: true }` 先审后 `next()`）自然组合——Auto Review 的 deny 在我们上游转 `askUser`，我们返回的 ask 会被其下游 `next()` 原样保留。`ask` 经 `serviceAsk` → `ctx.approval.request` → answerer waterfall；`allowed-once` 才放行；未挂 approval 服务时 DSH 原生退化为拒绝（fail-closed）。
3. **内置名单收窄**（窄名单删减版，用户确认）：保留具名凭据 basename（SSH 具名私钥、`.npmrc`/`.pypirc`/`.netrc`/`.pgpass`/`.git-credentials`/`.credentials.yaml`/`.auteur-media-secret`、Hive/转储文件及事务日志前缀）、`~/.aws/credentials` 与 system32 hive 三段组合；退役目录段（`.ssh`/`.aws`/`.kube`/`.gnupg`/`.pki` 整目录）、密钥后缀（`.pem`/`.key`/…）、浏览器/DPAPI/云 CLI 组合——混合载体（`.kube/config` 等）由用户 `sensitiveFiles` 显式标记。`.pub` 保持排除。`~/.ssh/config` 的 DSR-013 例外在新模型下自动成立（无目录规则可触）。
4. **操作面只拦读取**（用户确认）：`read` / `read_image` / `grep` 的显式单文件路径；`glob` 与目录级搜索永不触发（精确路径等值判断使然）；写/改/删全部交给 Auto Review 与 OS 权限。
5. **配置 Schema（全 `.volatile()`）**：`sensitiveFiles: string[]`（精确绝对路径；相对路径、通配符挂载即失败——「少量精确路径、不支持宽泛通配」的研究建议按用户确认采纳）+ `credentialsReadAsk: boolean`（内置名单开关）。客户端卡片 = 内置开关 + 每行一个绝对路径的编辑器，沿用官方 `SettingsFormModel`/`SettingsForm` 布线（`plugins.row.config`，键不变）。
6. **退役 PowerShell 静态解释器**：`check-command.js`/`command.js`/`destructive.js`/`deny-messages.js` 与语料回放工具（`tools/corpus-replay.mjs`，其日志格式知识已随 format v4 过时）删除；`unverifiable`/`destructive`/`env`/`git`/`system` 配置键随类别一并退役。
7. **peer 抬到 `^0.2.0-rc.2`**：门禁判定为 `semver.satisfies(runtime, range, { includePrerelease: true })` ⇒ 0.1.7-rc.2 的 stable-dev 上该行被静默禁用，README 写明升级顺序；旧运行时继续用 v1.7.0 发布物。

## 0.2.0-rc.2 核查记录（实施前，2026-10-16，本机源码检出 @ `639ed015`）

- `PreToolDecision`：allow / deny(reason, info?) / ask(reason?, displayReason?) / cancel（`packages/core/tools/src/index.ts:607-611`）。
- 管线：`pre-execute` waterfall → `serviceAsk`（`ctx.get('approval')` 缺失即拒绝）→ 单调 guard（`:1489-1539, 1727-1768`）。
- Approval 桥：`ApprovalService.request` 审计 `approval/asked`+`approval/decided` 对，`policy: 'ask'|'never'`（`packages/interaction/user-approval/src/index.ts`）。
- **T-A 核查结论**：审批链零等待超时（user-approval 源码、UI answerer、docs 全文 grep timeout/setTimeout/expire 均无命中）；现存的 120s 是 `tool-ask-user` 问答工具与 PTC 程序级 `timeoutMs`，均不在共享审批通道。无人值守姿态 = 会话 `approval policy = never`。
- settings 模型与 v1.7 相同（volatile + configForms + namespace=entry id；CHANGELOG §07 仅 config-editor 选择分支变化，不影响本插件）。

## 后果

- 单测矩阵重写：58 例全绿（行覆盖 99.22%）；V1 的 162 例随其被测对象退役。
- 误伤面大幅收窄：普通 `.env` 读取、`.git` 内部读取、系统区读写、全部 pwsh 命令不再被本插件触碰。
- **保护面同步收窄**（显式接受的代价）：shell 间接读取、宽搜索、PTC 直接 Node、其他进程完全不设防——这是「复用原生审查 + OS 权限」分工的既定取舍，README「有限覆盖声明」明确披露；需要强保密的场景必须上 OS 级隔离。
- 无人值守挂起风险维持现状（审批无超时），缓解手段是 `never` 策略；T-A 的 Host 侧实现不在本插件范围。
- verify 第 3 步「test 恰一行」在 test profile 重挂本插件前会报 0 行——这是 0.2.0 升级时「卸载全部插件」后的部署态，不是代码缺陷；重挂后复查。

## 重访条件

- DSH 原生审批若引入可配置等待超时（T-A 落地上游），本插件文档与无人值守指引随之更新。
- 若用户工作流证明内置名单漏防频繁，逐项增补 basename/组合，不恢复目录级与后缀规则。
- Auto Review 从 experimental 转正或策略可配置时，重核「ask 在其下游被保留」的组合行为（当前为 prepend 组合推断 + 源码阅读，未实例实测）。
