# DSR-018：内置敏感文件名单改名

**决定 / 理由 / 被否决项：** 把配置键 `credentialsReadAsk` 与设置页「内置凭据文件保护」改为 `builtinSensitiveAsk` / 「内置敏感文件」，让名称覆盖名单外延与已扩展的内容操作语义；否决保留旧名、只改提示、以及为旧键加别名。

- 日期：2026-10-17。
- 状态：源码已改，包版本 3.2.0，未发布；未重装、未重启 test 实例，运行中的实例经 HMR 已热加载新模块。
- 取代 [DSR-017](DSR-017-官方AST与最终硬门禁.md) 第 5 条「保留 `credentialsReadAsk` 配置名」的表述；DSR-001…017 其余原文不变。

## 上下文与备选

旧名沿用的理由是兼容更早配置，但事实是：`credentialsReadAsk` 由 2.0.0（`6e5d506`，2026-10-16）引入，从未进入 v1.7.0——后者 Config 为 `env`/`git`/`credentials`/`system`/`destructive`/`unverifiable` 六类；本机 test、stable-dev、dev 三个 profile 的 patch 也都没有该键或 `sensitiveFiles` 的持久值。它只属于一条未发布、无用户的开发线。

名单实际包含四类：SSH 私钥、工具凭据文件（`.npmrc`/`.pypirc`/`.netrc`/`.pgpass`/`.git-credentials` 与 DSH 凭据文件）、Windows 系统凭据库与用户配置单元（`SAM`/`SECURITY`/`SYSTEM`、`ntuser.dat`/`usrclass.dat` 及其日志）、分页与休眠文件（`pagefile.sys`/`hiberfil.sys`）。DSR-017 又把触发面从「读」扩到读/导出/写/删/移。

| 方向 | 评价 |
|---|---|
| 保留 `credentialsReadAsk` 与「内置凭据文件保护」 | 与名单外延、动作范围都不符，名称会长期误导 |
| 只改显示名、保留键 | 用户可见文案变准，但配置键里的 `Read` 仍误导维护者与配置审阅 |
| 改名并保留旧键别名 | 无持久化数据可迁，别名只会延长两套词汇并存 |
| `builtinSensitiveAsk` + 「内置敏感文件」 | 选定；与「自定义敏感文件」构成一对，行为零变化 |

## 决定

1. Config 键改为 `builtinSensitiveAsk`（boolean，默认 `true`，`.volatile()`），`RULE_KEYS` 与挂载期校验同步；无别名。
2. 设置页第一个字段标签改为「自定义敏感文件」/“Custom sensitive files”，开关改为「内置敏感文件」/“Built-in sensitive files”，提示列出私钥、工具凭据文件、系统凭据库、分页与休眠文件四类。
3. 不提供旧键兼容：旧键按现有 `unknown config key` 在挂载时显式失败（fail-closed、报错可见），依据是本机三个 profile 均无持久化值且 3.2.0 未发布。若日后出现已发布配置，再按迁移需要补别名。
4. 内部标识不随本次改名：`CRED_BASENAMES`、`pathTargetsCredentials`、`checkSensitiveRead` 的 `'credentials'` 返回值描述匹配器与名单内容，不是用户配置契约；改它们只会扩大改动面。
5. 行为、判定、审批与遮罩语义不变；验证套件只更新键名断言。

## 影响与未验证

- 影响面：Host Config schema 与规则求值（`host.js`/`rules.js`/`path-check.js`/`targets.js`）、设置页读写与双语字典、10 个测试文件、README、CHANGELOG、规则模型文档；新增本记录。
- 现场：改名后未重装 bundle、未重启实例。运行中的 test 实例由 HMR 热加载新模块，Host `Config.listConfigs`（`include:guardrails`）显示 `builtinSensitiveAsk`，说明 schema 已切换；设置页需刷新页面取得新客户端文件。安装记录与完整启动门禁仍属未复验项。
- 历史记录不回改：DSR-015/017 原文、部署文档里 3.1.0 及更早的旧键与旧审批文案都属当时证据。
