## 上下文

- 现状（DSR-004 落地）：五类别布尔开关（`env` / `git` / `credentials` /
  `destructive` / `system`），缺省全开，非法配置挂载即失败；敏感名单硬编码。
- 新需求（2026-08 用户提出）：**重构整个插件，将所有防御层都改为可配置项**，
  即每个防御层可以独立选择开启/关闭（"选择开启/关闭某种防御"）。
- 评估结论：类别级开关已存在且可用；真正的缺口有四个——

  1. `destructive` 内部 8 个规则族共用一个总开关（粒度最粗、误伤面最大：
     `kubectl delete`、`docker system prune` 等常规开发操作被拦，且无法只放松
     它们而保留关机/盘根删除类保护）；
  2. `assessUnverifiable`（动态目标 fail-safe）不可关——类别无关兜底层，
     README 明示"与类别开关无关"；
  3. 操作级（读 / 写 / 列举）无法细分：DSR-002 的"敏感类别 × 操作类型"矩阵
     只是内部实现，未暴露为配置面；
  4. 无档位预设（本决议明确不做，见下）。

## 真实方向与评价

### A. 全量叶子配置（本决议采纳）

类别键由 `boolean` 扩展为 `boolean | object`，把每个防御层归一化为布尔叶子：

- **评价（支持）**：防御层清单与现有实现一一对应（见"防御层 → 配置映射"），
  配置面 = 检测层的正交化，与 DSR-002 文档模型一致；v1 布尔写法全部向后兼容，
  已有 profile 用户层 id 合并不受影响；误伤消除的出路从"整类关闭"精化为
  "关闭某一子层"，安全保留面更大。
- **评价（反对）**：配置面扩大约 3 倍，校验与测试矩阵随之胀大；子键继承/
  合并/缺省语义必须精确界定，否则出现"看起来关了实际开着"的静默降级。
  → 对策：归一化 + 全部子键显式枚举校验 + 缺省继承 true（关必须显式），
  非法值沿用挂载即失败。

### B. 预设档位（`level: full | standard | relaxed`）——不做

纯语法糖：不增加任何能力，新增第二个配置维度（level 与单键的优先级与合并
语义）与校验规则。维持 DSR-004"不做推测性灵活性"的精神；若将来出现
"≥2 个 profile 需要固定档位且频繁切换"的具体场景，再重访。

### C. 三态开关（block | warn | off）——不做

warn 模式 = 放行交给 harness 常规权限管线，语义退化为"提示器"，与本插件
"硬阻断（不弹框、无运行时通道）"的身份冲突；也是安全上最弱的配置。
若有"观察不拦"需求，等价做法是关闭对应类别（测误伤）或删掉该 profile 的
guardrails 行。

### D. 名单配置化——维持 DSR-004

DSR-004 反对的是**敏感名单配置化**（自定义路径），本决议是**开关层级拆分**，
两者不冲突；自定义名单（config 声明额外敏感路径）依旧不提供。

## 最终决定

v2 配置 Schema（向后兼容；缺省 = 全部开启 = 当前行为）：

```yaml
config:
  env:          { read: true, modify: true }   # 或布尔 true / false
  git:          { read: true, modify: true }
  credentials:  { read: true, modify: true, list: true }
  system:       { write: true }
  destructive:  { git: true, machine: true, eval: true, cli: true, bulk: true, target: true }
  unverifiable: true                            # 新增键，缺省开
```

### 语义规则（`evaluateRules` 归一化）

- 类别键接受 `boolean | object`：
  - `false` = 整类关闭（子键忽略）；
  - `true` 或未提供 = 整类开启；
  - `object` 内子键**缺省继承 true**（关闭必须显式写 `false`），未知子键报错。
- 归一化后的内部结构（判定层只消费叶子）：

```js
{
  env:          { read, modify },
  git:          { read, modify },
  credentials:  { read, modify, list },
  system:       { write },
  destructive:  { git, machine, eval, cli, bulk, target },
  unverifiable: boolean,          // 顶层布尔
}
```

- 非法配置（未知键、非布尔、数组、null 等）在挂载时失败并给出可操作错误
  （沿用现有质量线，`lifecycle.test.mjs` 已覆盖同款语义）。
- 工具名清单（`read/write/edit/read_image/grep/glob/pwsh`）属"防御面"，
  不属防御层：**本次不做**（列为 P2 独立需求，需各层适配参数结构）。
- 字面量重建（`resolveCommandLiterals`）是检测机制而非政策层：**不提供开关**
  （关闭即产生 `$p='.env'; Get-Content $p` 类同名绕过）。
- 钩子层 fail-open（防死锁）维持固定，不配置化。

### 风险标注（写入 README）

- `destructive.target` 关闭 → 盘根删除 / 工作区根删除 / 动态 cd 删除**放行**，
  属绝对破坏语义层；README 显著标注风险等级。
- `unverifiable: false` → 动态 `$()` 目标的内容/删除命令放行（检测力下降），
  括号内注明"仅建议受控 profile 使用"。

### 配置覆盖（v2）

防御层全量配置化：每个防御层都是独立开关，缺省全开（关闭必须显式写
`false`，子键缺省继承 `true`）。类别键接受布尔（= 整类开/关）或对象
（= 按操作细分）：

```yaml
- id: guardrails
  config:
    env:          { read: true, modify: true }   # .env 路径内容访问（读/写）
    git:          { read: true, modify: true }   # .git 内部内容访问（读/写）
    credentials:  { read: true, modify: true, list: true }  # 凭据 读/写/列举
    system:       { write: true }                 # 系统区写入（W0）
    destructive:
      git: true      # git reset --hard / clean -f / force push / branch -D ...
      machine: true  # 关机/磁盘/net user/杀进程/iex 等机器级命令
      eval: true     # 不可信内容执行（curl|bash、.NET 直调）
      cli: true      # docker prune / terraform / kubectl / aws s3 rm / dropdb ...
      bulk: true     # Get-ChildItem | Remove-Item 管道批删
      target: true   # 盘根/工作区根/动态 cd 删除目标分析（绝对破坏层，慎关）
    unverifiable: true  # 动态 $() 目标 fail-safe（慎关：检测力下降）

# 例：test 环境放松——只对 CLI 数据破坏器降级：
- id: guardrails
  config:
    destructive: { cli: false }
```

- 非法配置（未知键、非布尔、非对象）挂载即失败，不会静默降级。
- 关闭任意一个防御层前，请先阅读 README"已知限制与边界"中对应条目的风险
  标注；`destructive.target` 与 `unverifiable` 关闭后对应拦截**完全放行**。
- v1 五键布尔写法依然有效（等价于对应类别全开/全关）。
