# DSR-016 — 插件自有审批超时（收窄 T-A 的边界）

- 日期：2026-10-17
- 状态：已实施（代码与单测；实例级实测待重启后补）
- 取代：DSR-015 §决定 T-A 中「全插件一律不计时」的**范围**（不是推翻其结论）
- 上游依据：DSR-015 `docs/decisions/DSR-015-审批式敏感读与职责收缩.md`；本文只补它的超时空白

## 背景

DSR-015 的 T-A 结论有两条：

1. DSH `0.2.0-rc.2` 原生审批链**没有等待超时**（源码核查属实，见下）；
2. 因此「统一等待上限」属 DSH Approval Service / Host answerer 的公共边界，本插件不实现。

T-A 的**事实**仍然成立，但它的**边界划分**留下一个洞：无人值守时一次无人点击的弹窗会让工具调用**永久挂起**（不是"等一会儿自己拒"）。用户 2026-10-17 要求评估能否自理，结论是能——`approval.request` 把 `signal` 放在公开契约上，且客户端弹窗会随 `signal` 中止自动收起。于是把 T-A 收窄为：「**全局**等待上限仍属上游；本插件对自己发起的 ask 提供可选上界」。

## 决定

1. **配置项 `askTimeoutMs`**：整数毫秒，`0` = 关闭（默认，保持 DSR-015 原有语义），上限 `3600000`。全 `.volatile()`，设置页可直接改、改后即生效（不重启）。
2. **`0` 时走原生 `{ kind: 'ask' }`**：一行代码都不接管，行为与 DSR-015 完全一致。
3. **`> 0` 时插件自己发请求**：`ctx.get('approval').request({ agent, toolName, callId, reason, signal })`，`signal = AbortSignal.any([exec.signal, 自建 controller.signal])`，到点 abort 自建控制器。
4. **超时即拒绝（deny），不是 cancel**：文案明确「这是自动拒绝，不是用户拒绝，不要用同一参数反复重试」，并说明命中类别。cancel 只留给**调用方取消**（`exec.signal` 中止、非我方计时器），以保留原生的 aborted 语义。
5. **结果映射与 `tools/serviceAsk` 逐字对齐**：`allowed-once` → allow；`rejected` → `the user rejected tool "x"`；`unavailable` → 无通道文案；词表外的值一律按拒绝处理（闭合词表，绝不把未知读成放行）。映射落在 `src/core/ask-decision.js`（纯数据、可裸 Node 测试）。
6. **失败方向**：判定层异常仍 fail-open（DSR-015 不变）；但**已经判定命中后的审批层异常一律 fail-closed**（无 approval 服务、无 agent、请求抛错 → deny），因为此时放行等于静默跳过审批。
7. **只约束本插件发起的 ask**：Auto Review 等其他来源的弹窗不受影响，README 与配置页文案必须写明，避免"全局已有超时"的错觉。

## 机制核查（2026-10-17，`versions\0.2.0-rc.2` 安装树，非推测）

| 事实 | 位置 |
| --- | --- |
| `approval.request(req)` 接受 `{ agent, toolName, callId?, reason?, signal? }` | `@deepseek-ai/dsh-user-approval/lib/index.js` `request()` |
| `decide()`：`signal?.aborted` 即 `cancelled`；策略 `never` 在 answerer 之前短路为 `rejected`；带 signal 时与 answerer 竞速 | 同文件 `decide()` |
| 弹窗侧监听 `request.signal` 的 `abort` 并 `abort()` 该 pending 审批（弹窗随超时收起） | `@deepseek-ai/dsh-client-ui-approval/lib/client.js`（`PendingApproval` 构造与 `abort()`） |
| 原生 ask→决策映射（本次照抄） | `@deepseek-ai/dsh-tools/lib/index.js` `serviceAsk()` |
| `tools/execute` 的超时策略只包执行阶段，不含审批等待 | `@deepseek-ai/dsh-tool-call-timeout-policy/lib/index.js`（挂 `tools/execute`） |
| 审计对 `approval/asked` + `approval/decided` 由服务无条件写入 | `request()` |
| 唯一间接上界：PTC `run_code` 程序预算「含嵌套工具与审批等待」 | `@deepseek-ai/dsh-tools` 程序超时参数说明 |

## 后果

- **审计可读性有限**：服务的结果词表封闭，超时与「用户取消回合」在日志里同为 `approval/decided: cancelled`。区分只能靠插件侧另记一行 `[guardrails] ask timed out after Nms`（已实现）。
- **文案必须与原生一致**：接管后我们复刻 `serviceAsk` 的四种文案；若上游改文案，这里要跟。
- **等待期间 UI 行为**：超时后弹窗由客户端按 signal 收起；若客户端未订阅（未来代际变化），会出现"弹窗在但请求已结束"，属重访条件。
- **覆盖面**：只覆盖 guardrails 的 ask。无人值守的**完整**解法仍是会话 `approval policy = never`（立即确定性拒绝，零等待）。
- 默认关闭意味着：不配置就仍是"永久等待"。这是刻意选择——静默改变默认语义的代价大于收益。

## 重访条件

- DSH 原生审批引入可配置等待上限（T-A 上游落地）→ 删除本插件计时器，回到纯 `ask`。
- `approval.request` 的 signal 语义或结果词表变化 → 重核本文第 5、6 条。
- 客户端不再随 signal 收起弹窗 → 超时机制需改为 deny 前先通知 UI（当前无此通道）。
