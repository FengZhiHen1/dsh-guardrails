# DSR-036 输出面契约与文案分层

- 日期：2026-11-21
- 状态：已决定

## 背景

输出面（拒绝块、确认卡、通知、遮罩标记、配置告警）此前把两类读者混在一起：面向 agent 的拒绝块偶有「`not captured`」空话、`APPROVAL_POLICY_NEVER` 同时承担「策略禁止」与「无通道」两种含义、超时给不出类别化下一步；面向用户的确认卡残留内部字段名与标记 token，中文卡混入未标注英文；遮罩标记不带类别，结构化 `value` 分支因无法安全投影而被跳过；配置问题降级后没有任何日志。用户批准了一次「输出面全面审计修复」（批 1 + 批 2 + 安全项），要求把读者与文案契约分开。

## 决定

**受众分层原则**：面向 agent 的文本（拒绝块 5 个字段 Why/Trigger/Effect/Scope/Next、空字段省略；通知；拒绝码）以**英文、准确、可执行、信息充分**为准；面向用户的文本（审批卡、设置页、插件元数据）以**中英、人话、单段、不泄露内部 token** 为准。两类文本可以共享同一份事实，但不共享措辞风格。

1. **拒绝文案统一、归因拆分、下一步分类**
   - 所有拒绝文案显式声明 `nothing was executed` /「未执行任何操作」。
   - `APPROVAL_POLICY_NEVER` 只表示「会话策略/开关禁止」（策略为 `never` 且 `alwaysAsk` 关闭）；「无确认通道」改用既有 `APPROVAL_UNAVAILABLE`，不再把两种情况混成一个码。
   - `APPROVAL_TIMEOUT` 按规则类别给不同下一步：目标可枚举类（删除/受保护命中）建议收窄到更少、字面的目标后重试；其他类建议等用户可响应时重试或手工处理。预算耗尽用同一码的最短提示。
   - 所有 `deny` 的 `Next` 统一带 `Nothing was executed.`（含 catastrophic、未知 stage、`execution.check-failed` 与 guard fault）。

2. **拒绝块与故障文案**
   - `execution.check-failed` 的 `Trigger` 使用真实 stage/gap 码，不再输出 `not captured` 占位空行。
   - `renderDecision` 不再输出 `Trigger: not captured`；无证据时省略该行或给出可解释原因。
   - 已知 stage 由 `STAGE_META` 提供专用 `Effect`/`Next`；未知 stage 用通用文案。
3. **配置问题写日志**：`configIssues` 去重后接 `logger.warn`，消除「降级但无日志」的静默。对外仍按保护性默认工作（R-20 不变）。
4. **确认卡文案**：
   - `data.git.worktree` 与 `data.move.source` 用专用句式（移除工作树 / 移动后源位置不再保留）。
   - `notes` 必须渲染：已知标记按映射转写，未知标记标注「原文：…」。
   - 中文卡不混未标注英文；动作 token 全部中英映射。
5. **通知**：首行人话说明，后接中性字段 `rule=`、`confirmed_by=answerer`、`channel=approval-card` 或 `channel=question-card`、`scope=`、`this_call_only=yes`；`scope` 为人话摘要并截断。通知只对**经确认应答方（可能是用户）放行**、仅接受且非错误时注入。
6. **遮罩与 withhold**：标记带类别 `[REDACTED:<kind>]`（`kind ∈ pem/bearer/jwt/provider`）。仅当值是**纯字符串**且输出 schema **无约束**（无 enum/const/pattern/format/length 等）时，原位替换为 `[REDACTED:<kind>]`；其它类型或受约束 schema 的值若含可遮罩内容，**不替换、改为 withhold（block）该结果**，返回一条不含原值的说明（`This result was withheld…`），以避免运行时 `invalid output` 回显原文。这是**安全优先**取舍。补齐以下安全策略：
   - **错误结果**：`result.error.message`、`result.error.info`、`result.meta` 命中或 `unknown` → 整条 **withhold**（模型/PTC 只见固定说明，无原文）。
   - **block.info**：命中 → 替换为 `{ name: 'Guardrails', code: 'REDACTED' }`，保留 block 渲染与错误身份。
   - **meta 类**：`result.meta` / `presentationMeta` 命中或 `unknown` → withhold（`PostToolDecision` 无 meta 字段，不能原位替换）。
   - **content 分支**：`decision.content` 分支同时扫描 `value`、`result.value`、`meta`，命中即 withhold（content 替换仍会向 PTC 暴露 value）。
   - **additionalContexts**：`decision.additionalContexts` 任一条消息 `scan !== 'clean'`（含 text 块含凭据）即整条丢弃该条 context，不做局部遮罩；工具自身 `result.additionalContexts` 的非 text 块（image/file）**深扫 clean 即放行**，命中/`unknown` → **整条结果 withhold**。
   - **非 text 字段与块**：除 `text`/`name`/`attachment.name` 外，`reasoning` 的 `text`、`tool-call` 的 `arguments`、contexts 消息的 `source.summary` 等非 content 字符串字段都参与遮罩；未知块类型整块深扫，命中/`unknown` → withhold。
   - **presentationMeta**：只投影一次，避免重复调用产生副作用。
   - **containsMaskable 三态**：`hit|clean|unknown`；越过 depth 32、单数组 65536、对象键 65536、单字符串 8MB，或 `Map`/`Set`/`Buffer`/`Date`/类实例 → `unknown` → **按不安全处理并 withhold**；clean 的超大但未越界对象/数组正常放行（与 EX-04 一致）。
   - **PTC durable log（`tools/ptc-dispatch-log`）专用遮罩**：对日志中每个 JSON 字符串值做遮罩（覆盖 `id`/`payload`/`arguments`/自定义字段，不依赖字段白名单）；已知块类型且 clean → 原样；未知块类型、非 JSON、循环、超上限（depth 32 / 数组键 65536 / 8MB）→ **整块占位**（比结果面更严格）；`next()` 返回非数组或抛错 → 单条固定占位，防止 PTC runtime 失败回退把原始 content 写入日志。

## 理由

- 拒绝块是给 agent 的执行指令：准确、信息充分、可行动的英文比本地化更重要；确认卡是给人看的：人话、中英、单段比字段完整更重要。
- 把「策略禁止」与「无通道」拆开，agent 才知道该请用户改设置、还是换一个能应答的会话；超时按类别给下一步，避免对删除与对普通操作给同一条无差别建议。
- `not captured` 与未标注英文会稀释可信度；真实 stage/gap 码让故障可定位。
- 遮罩的目的是降低泄漏面，不是维持「不可投影就放行」的旧保守逻辑；带类别标记也便于日志与审计分辨遮罩原因。受约束 schema 上强行替换会触发运行时 `invalid output` 并可能回显原值，因此宁可 withhold。
- 配置降级不写日志，会让维护者以为配置生效；`logger.warn` 是消除静默降级的最小手段。

## 被否决项

1. **给拒绝块加中文行**。否决：拒绝块的第一读者是 agent，双语会拉长提示、稀释可执行信息；中文化属于面向用户的确认卡与设置页。
2. **把内部 flag 显示给用户**。否决：`git-metadata-inside-tree` 一类 token 对用户无意义，且暴露实现细节；只保留人话映射，未知项仅在审计原文出现。
3. **仅改遮罩标记、不处理 `value` 分支**。否决：标记变了但结构化 `value` 仍可能带明文，等于没降低泄漏面；`value` 分支必须同时处理（可原位替换则替换，否则 withhold）。

## 已知取舍与残留

- `ask` 通道共享卡的说明仍是**标题槽**：平台不传独立 `description`，因此摘要占标题位置；单段不可换行是平台卡约束。
- `result.isError` 的 `value`：运行时通常会拒绝替换失败结果的 value；插件仍做防御性 withhold（纵深防御），并有 hook 级测试。
- **结构化结果可能被整体 withhold**：受约束 schema 或非纯字符串的值一旦含可遮罩内容，就不原位替换、直接 withhold，调用方会失去该结果；这是安全优先的已知限制。
- **有界扫描按不安全处理**：深度上限 32、单数组/对象键最多 65536、单字符串上限 8MB；clean 的超大但未越界对象/数组正常放行；越过任一边界或 `Map`/`Set`/`Buffer`/`Date`/类实例等非 plain object → `unknown`，按不安全处理并 **withhold**（与 EX-04 一致）。
- 拒绝块长度有上限，超长范围在 `Scope` 截断；不声称覆盖全部细节。

## 后果

- 拒绝时 agent 看到英文块，含真实 stage/gap 码与「未执行」声明；超时按类别给下一步；`APPROVAL_POLICY_NEVER` 与 `APPROVAL_UNAVAILABLE` 不再混用。
- 用户看到中英单段确认卡；worktree/move 有专用句式，`notes` 可见，中文卡无未标注英文。
- 确认应答方（可能是用户）放行后的通知带人话首行与中性字段；`scope` 为截断的人话摘要。
- 纯字符串且无约束 schema 的遮罩输出 `[REDACTED:<kind>]`；含可遮罩内容的结构化/受约束结果整体 withhold 并返回不含原值的说明。
- 配置问题有 warn 日志；行为仍按保护性默认。
- 保守拒绝在 `Next` 写明可执行的替代策略（见规则模型「保守拒绝与替代策略」）。

## 证据与验证

**可由源码/公开契约证明的**：

- `ApprovalRequestEvent.displayReason` 与 `AskUserQuestionIntent.display` 是公开展示字段（`@deepseek-ai/dsh-user-approval`、`@deepseek-ai/dsh-user-questions`）。
- `PostToolDecision.additionalContexts?: UserMessage[]` 是公开契约，`notice` 需 `summary`（`@deepseek-ai/dsh-tools`、`@deepseek-ai/dsh-llm`）。
- `conversation.approval.card` 的 `ApprovalCardInput` 无独立 description 以外的可换行能力；共享卡说明按单段渲染（`@deepseek-ai/dsh-client-ui-approval`）。
- 工具输出 schema 的约束（enum/const/pattern/format/length）可由注册的工具定义读取，用于判定「可原位替换」还是「必须 withhold」（`@deepseek-ai/dsh-tools` 的 `output.schema`）。
- 本仓库实现点：`src/adapter/dsh-gate.js` 的拒绝文案与 `displayReasonOf`；`src/adapter/confirm-text.js` 的 `confirmSummary`；`src/core/decision.js` 的 `renderDecision` 与（本轮新增）`STAGE_META`；`src/adapter/redaction.js` 与 `src/core/redaction.js` 的遮罩/withhold；`src/adapter/host.js` 的 `configIssues` 日志。

**待实测（本轮没有实测证据，不得写成已验证）**：

- 真实拒绝块在 GUI/日志中的 5 行呈现、`Trigger` 真实码与「未执行」声明；
- `APPROVAL_POLICY_NEVER` / `APPROVAL_UNAVAILABLE` / `APPROVAL_TIMEOUT` 在真实会话中的文案与下一步；
- 确认卡 worktree/move 专用句式、`notes` 渲染、中文卡无未标注英文；
- 通知首行与 `rule/confirmed_by/channel/scope/this_call_only` 字段在真实会话下一步可见；
- `[REDACTED:<kind>]` 的原位替换、以及受约束/结构化结果的 withhold 在真实工具结果中的输出；
- `configIssues` 的 warn 日志确有一次去重记录。
