# DSR-009：无状态边界——同调用链删与参数误用入闸，会话状态与 approval 档否决

## 上下文

2026-09-10 发生一起 AI 会话误删事故（用户侧真实数据损失，事后复盘）：同一条 pwsh 调用内
`Move-Item -LiteralPath "$in\*"`（`-LiteralPath` 不展开通配符 → 非终止错误、零文件移动）后接
`Remove-Item "$in" -Recurse -Force`（默认 `-ErrorAction Continue` 不设门 → 对原封未动的
唯一副本目录执行递归强删；E: 为 NVMe+TRIM，删除近似永久），且"完整性校验"写在删除之后，
不构成事前闸门。

**复演取证（2026-09-10，纯静态直调 `checkCommand`，全防御层开）**：该事故命令形态被现行规则
**完整放行**——三个信号各自都在盲区（该复演已固化为测试用例：`test/destructive.test.mjs`
「incident replay」、`test/guard.integration.test.mjs`「DSR-009」）：

1. `-LiteralPath` 携带通配符：任何子族不认识这个语义错误（词法层无信号）；
2. 无错误门的"变异 → 递归强删"串联：`bulk` 只管管道批删，`target` 只管盘根/工作区根/`*`，
   `-Recurse`/`-Force` 标志本身不在任何判定里；
3. 删除目标是普通子目录（唯一副本）：判定层无法从命令文本知道"唯一副本"——这需要跨调用状态。

附带取证：现行词法把 `&&`/`||` 压扁为单字符 sep——"有无错误门"在词法层就已丢失，是形态 2
检测的先行缺陷。

## 真实方向与评价

### A. 纯静态扩闸（本决议采纳）

`misuse`（参数语义误用 lint：`-Literal*` 带通配符 = 永不可解析的必败语句；removal/mutator
动词的 `-Path`/位置目标含 `[ ]` = PowerShell 通配字符类，会命中从未指名的文件）+
`chain`（同调用内 mutator → 无 `&&` 门 → 带 `-Recurse`/`-Force`/`-r`/`-f`/`/s` 的 removal；
`-ErrorAction Stop` 视为门）两个新子族，另加词法分隔符保真（`&&`/`||` 保留双字符原值）。

- **评价（支持）**：全部在既有词法/片段模拟能力圈内，零新依赖；三条判据即事故复盘给出的
  可操作判据的机械子集；deny message 直接携带正确流程（消息通道实证有效——本次开发会话中
  插件的拦截消息两次使模型当场改写命令）。
- **评价（反对）**：对"隔一回合再删"（move 成功落位后单独发删除）依然无闸——这是无状态的
  结构极限，不是实现不足。→ 由决议 C 的规程层承担。

### B. 会话级 move journal（否决）

按 session 记录本会话 move/rename 的目的路径；removal 命中"近期接收过移动的目录"即拦——
唯一能机械识别"唯一副本"的方案，可封死跨回合形态。

- **否决理由**：插件身份 = 纯静态文本判定（需求 C-01/R-10：无状态、无 fs、判定只依赖本次
  调用参数）。引入跨调用状态牵出整条新链：fiber dispose/HMR 下的状态生命周期、会话键与
  subagent 边界（跨会话即失忆）、路径别名等价（subst/网络盘，判不准就漏）、内存上界与 LRU
  语义、以及"journal 判据错杀"与"journal 漏报"的双向误伤论证成本。收益只覆盖 A 覆盖不了的
  "跨回合删"一个形态，不成比例。
- **关键性质**：B 不解决 A 的误伤问题（它更严），只解决漏报；而它的漏报面（别名、跨会话、
  脚本文件内 move）并不比 A 小多少。

### C. approval 档（ask）——维持 DSR-006 否决，本处重申

`tools/pre-execute` 的 `ask`（挂 approval 时弹框、未挂退化拒绝）可给 `chain` 这类
"意图合法但写法危险"的形态一个协商出口。但插件身份是"硬阻断，不弹确认框"（需求 R-02）；
ask 把每次误伤变成用户现场的弹窗谈判，且引入 `@deepseek-ai/dsh-user-approval` 依赖与运行期
交互通道。A 的误伤出路已有非交互通道：叶子开关（profile 级、用户主动配置）+ 用户手动执行。

## 最终决定

1. 采纳方向 A：新增 `destructive.chain` 与 `destructive.misuse` 两子族（缺省开，随 DSR-006
   叶子语义可独立关闭），并做词法分隔符保真；v1.5.0 落地。
2. 否决方向 B：**无状态边界重申为本插件的构成性约束**——跨回合（分离调用）的删除时序问题
   不属插件判定面。该缺口由顶层仓库 AGENTS.md 的"破坏性命令纪律"规程补偿（软约束层），
   README 已知限制如实标注，防止后人误以为插件已兜底。
3. 方向 C 维持否决；若未来产品形态要求"删除前人机确认"，那是宿主 approval 管线的需求，
   不是本插件的身份扩展。
4. `chain` 不建模 `try/catch`、`if ($?)`、`$ErrorActionPreference` 等控制流级门控（词法层
   不建语句依赖图）：此类串联会误拦，出路是拆回合（本就要教的正确写法）或关叶子——接受。

## 直接后果

- 破坏性分析子族 6 → 8；配置叶子、卡片、规则模型、命令文本分析、需求 R-03/R-07 同步。
- `tokenizePwsh` sep 值出现 `&&`/`||` 双字符形态：`bulk`/`eval` 的 `=== '|'` 判定语义不变
  （`||` 本就不是管道——顺带修复一处既有误伤面）。
- 已知边界新增（README）：跨回合删不判（无状态，DSR-009）；先 write 脚本文件再执行的
  链式结构对文本层不可见（防事故不防对抗，静态分析的定义性极限）；`[ ]` 通配判定按
  Windows FileSystem provider 语义（C-05 同前提）。
- 测试 +5 组（misuse 正反、chain 门控正反、`&&` 门/EA Stop 门、事故复演 + 双层独立 ablation）。

## 重访条件

- **同类跨回合误删事故再次发生** → 重估 B：届时按"规程层已被证伪"立新的状态化设计决议，
  而不是在 A 上打补丁。
- 出现"删除前人确认"的真实产品需求（多用户/远程场景）→ 评估 C 与宿主 approval 的分工。
- `chain` 误伤率在实际 profile 中高到需要细粒度豁免名单 → 重访 DSR-004（名单配置化）在
  规则参数上的适用性（仍不做敏感名单配置化）。
