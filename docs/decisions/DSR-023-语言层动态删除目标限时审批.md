# DSR-023 语言层动态删除目标限时审批

> **前向更新（2026-11-17）**：[DSR-025](DSR-025-定位重定位与判定模型重构.md) 把「动态删除目标 → 确认」推广到所有层（含命令行字面量目标）；本记录「命令行字面量目标仍拒绝」的区分被统一取代。

- 状态：已采纳
- 日期：2026-11-17
- 关联：DSR-019 删除计数与不确定执行拒绝、[需求](../需求.md) R-17、[跨语言删除分析](../technical-details/跨语言删除分析.md)

**决定 / 理由 / 被否决项：** 对 Python/Node 已识别删除 sink、但目标无法静态求值的情形，改为**插件自有一次性限时确认**（决策值 `ask`）；命令行字面量目标仍维持「未知即拒绝」。否决「一律拒绝」与「一律放行」；本决策显式修订 DSR-019「未知删除目标 → 拒绝」在语言层的适用。

## 背景

DSR-019/020 冻结的规则是「未知删除目标 → 拒绝」，针对的是命令行字面量目标。引入 Python/Node 静态删除分析（R-17）后，语言层的删除目标几乎总是计算得到的：`shutil.rmtree(os.path.join(tmp, name))`、`fs.rmSync(path.join(dir, f))`。照搬「求不出即拒」会让语言层分析大面积拒绝真实脚本，比不分析更不可用；照搬「求不出即放行」则等于给程序化删除开盲区。两者都是真实代价。

## 真实方向与评价

| 方向 | 安全 | 可用 | 说明 |
|---|---|---|---|
| A 求不出 → 拒绝 | 高 | 低 | 忠于 DSR-019 原文；语言层几乎全拒 |
| B 求不出 → 放行 + 记 unknown | 低 | 高 | 承认程序化删除是漏报面 |
| **C 求不出 → 限时确认**（选定） | 中高 | 中高 | 人在环内确认；保住「计数或确认」初衷 |

参考举证相反：DCG 对已识别不可验证的破坏汇 fail-closed，CCSN 把动态 sink 规则放在 `fail_closed` 能力位后（standard 默认放过）。二者不构成对 C 的否决，只说明这是真实取舍、需产品拍板。

## 决定

1. 语言层（Python/Node）已识别删除 sink、`AbstractPath` 为 `unknown` → 单一决策点产确认（决策值 `ask`）。
2. 确认由插件自有、一次性、限时（沿用 DSR-016）；批准只放行当前调用，批准后重新盘存该目标与计数；`never/超时/取消/迟到/不可用` 均不执行。
3. 命令行字面量目标的「未知即拒绝」不变（DSR-019 原义保留）。
4. 灾难身份不因本决策放松：脚本计算出的目标一旦求值命中根/设备/`.git`/系统树，直接拒绝。

## 直接后果

- `需求.md` 新增 R-17 并在删除计数条目注明语言层例外。
- 单一决策点增加「动态目标转确认」判定档，位于灾难身份之后、删除分档计数之前。
- 确认在语言层高频删除场景会产生交互；以 DSR-016 的超时与一次性语义约束噪声。

## 重访条件

若语言层动态目标确认在生产中噪声过大（例如大多数都能安全枚举），或求值器覆盖率显著提升到「几乎都能算出」，重访是否收窄为「能算则算、极少数才确认」。若出现确认被滥用绕过删除意图的证据，重访收紧方向。
