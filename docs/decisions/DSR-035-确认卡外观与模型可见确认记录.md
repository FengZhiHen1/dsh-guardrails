# DSR-035 确认卡外观与模型可见确认记录

- 日期：2026-11-21
- 状态：已决定

## 背景

[DSR-034](DSR-034-插件自有确认通道与never策略回退.md) 打通了 `never` 策略下的问答确认通道，但实际 GUI 中暴露三个问题：

1. **外观不像审批**：待答问题按通用单问题问答卡渲染，没有标准审批卡的标题、说明与「拒绝」「允许一次」操作区。
2. **未本地化**：选项按钮固定为英文 `Allow once` / `Reject`，中文界面下仍是英文。
3. **agent 不知情**：模型只看到工具输出，不知道这次放行来自人工确认、且只限当前调用，容易把它当成普通允许并复用。

用户要求：确认卡按标准审批卡展示并本地化；人工确认放行要让模型知道。

## 决定

1. **客户端半区新增确认卡选择器与组件**：`selectGuardrailsApproval` 只接管 `id === 'guardrails-confirm'` 且 `intent.kind === 'approval'` 的待答问题；其他提问返回 `null`，保持原渲染方。组件 `GuardrailsApproval` 在 Web 端经 composer 链 `renderFactorySlot('conversation.approval.card', …)` 复用平台共享审批卡工厂，渲染**标准审批卡**（标题/说明/「拒绝」「允许一次」），回答回传 `Allow once` / `Reject`。
   - 注册方式与首方 `dsh-cua` 相同：`ctx.slots` 的 `conversation.composer` 链 `select` 加 `inject({ resolveText: text => ctx.locale.resolveText(text) })`。
   - 客户端半区不 import 任何 Harness Client 包的运行时符号；composer 链 props 仅作类型借用，只用 `ctx.slots`/`ctx.locale`。
   - 该选择器只接管本插件的问题 id，不影响其他插件的提问。

2. **问题请求带本地化展示字段**：`askViaQuestions` 在请求上带 `intent.display = { question: { en, zh }, detail: { en, zh }, approve: { en, zh } }`。`en` 必填、`zh` 用小写键；`approve` 覆盖「允许一次」。允许按钮标签由插件传入的 `intent.display.approve` 覆盖（中英），只有拒绝等固定操作走 approval 语言包。因此：中英界面按 `intent.display` 显示本地化标题/说明/允许标签；非中英界面回退英文标题/说明与英文允许标签，拒绝等固定操作按客户端语言包本地化。

3. **说明采用单段人话摘要**：共享卡的说明区是纯文本，不渲染换行或 Markdown，因此 `intent.display.detail` 不拼多行、不塞 Markdown，而采用**单段、分号分隔、字段人话化**的摘要（目标 / 涉及目录 / 另将销毁 / 标记），长列表截断为「等共 N 项」；中英各一套模板；scope 解析失败时回退原始 `reason` 原文，不丢信息。

4. **模型可见的确认记录**：人工确认放行后，插件在 `tools/post-execute` 给模型下一步注入一条独立通知——`source.kind = 'dsh-guardrails'`、`form: 'notice'` 的 user 消息，内容含 `rule=`、`scope=`、`channel=(approval|question)`、`policy=(never|ask)`、`reusable=no`。只对**经人工确认**的放行注入；规则直接放行不注入。仅当该调用被下游接受（`kind='accept'`）且结果非错误时注入，下游 block 或错误结果不注入；同一 execution 读取即清除，最多一条。拒绝侧不改：`APPROVAL_*` 码仍在拒绝文案里（平台不把结构化 `info` 暴露给模型），也不额外注入通知。

5. **非 Web 客户端降级**：没有共享卡工厂的客户端（非 Web）经 `renderFactorySlot` 的 `fallback` 渲染最小卡片，仍保持「向用户展示一次确认」的语义。

## 理由

- 共享审批卡是用户最熟悉的确认外观，拒绝等固定操作随客户端语言包本地化、允许标签可由调用方覆盖；复用工厂比自绘或逐端适配维护面更小。
- `intent.display` 是公开的展示字段，`en` 必填 + 可选语言键，天然支持回退；不需要为本地化引入新的宿主契约。
- 模型需要知道「这次放行来自人工、只限当前调用」。`additionalContexts` 是公开的 post-execute 契约，比在工具结果里拼文本更干净，也便于后续按 `source.kind` 过滤。
- 不裸派发 `approval/request` 去复用审批卡：该通道的 scope 载体是 `dsh-scope` 模块私有，第三方插件不可用；且它会绕过会话 policy 与审批审计（`never` 下无法展示），与 DSR-034 的通道优先级冲突。

## 被否决项

1. **裸派发 `approval/request` 复用审批卡**。否决：scope 载体是 `dsh-scope` 模块私有、第三方不可用；且会绕过 policy 与 `approval/asked`/`approval/decided` 审计，`never` 下无法展示，和 DSR-034 冲突。
2. **改宿主权限预设**。否决：超出插件范围，会改变所有工具与其他应答方的行为，用户明确不要求改宿主预设。
3. **只改文案、不换卡**。否决：卡片仍是提问样式，用户不会把它当审批，也无法获得本地化的审批操作区。
4. **注入 `white-space: pre-line` 强制换行**。否决：依赖平台内部类名，跨版本脆弱，不属于公开契约。
5. **自绘卡片**。否决：多维护一套外观，本轮不做。

## 已知取舍

- **非 Web 降级卡**：无共享卡工厂的客户端只能显示最小卡片（标题/说明/两枚操作）；外观与可用性未实测，且与 Web 标准卡存在观感差异。
- **本地化覆盖有限**：问题标题、说明与允许标签只提供中英两种；允许按钮由 `intent.display.approve` 覆盖，拒绝等固定操作按客户端语言包本地化。非中英界面回退英文标题/说明与英文允许标签，故是「英文正文 + 本地化拒绝」的混合语言，不是完整多语言。
- **半内部消息构造**：`additionalContexts` 的消息对象按 `UserMessage` 形状手工构造（插件不能 import `dsh-llm`），属半内部构造；`PostToolDecision.additionalContexts` 是公开契约，消息对象本身需由测试锁定形状。
- **通知形态**：注入的是「下一步 user 消息」形态的 `notice`，不是工具结果的一部分；同一调用只注入一条；`reusable=no` 是文本声明，不是运行时锁，模型仍可能无视。
- **卡仍是单问题阻塞请求**：不改变 DSR-034 的通道、审计与拒绝码；`alwaysAsk = false` 时仍自动拒绝。
- **单段不可换行是平台卡约束**：共享卡说明区不渲染换行/Markdown，只能以单段摘要承载信息；信息密集时依赖分号与计数截断，不是富文本排版。

## 后果

- Web 且共享卡工厂可用：确认显示为标准审批卡（标题/说明/「拒绝」「允许一次」）；中文界面显示中文标题/说明/允许标签，英文界面显示英文；非中英界面回退英文标题/说明与英文允许标签，拒绝等固定操作按客户端语言包本地化；选允许回传 `Allow once`。
- Web 无工厂或非 Web 客户端：显示最小卡片，仍可做一次确认。
- 人工确认放行后：模型下一步收到一条确认记录；规则直接放行不注入；拒绝路径只保留 `APPROVAL_*` 文案。
- 通道优先级、`alwaysAsk`、一次性授权、完整重访与归因码全部沿用 DSR-034。

## 证据与验证

**已由源码/公开契约证明**（目标运行时 `0.2.2-rc.2` 安装树）：

- `AskUserQuestionIntent.display` 是公开字段，形状为 `{ question: { en, [locale] }, detail?, approve? }`，`en` 必填；语言键为小写（`@deepseek-ai/dsh-user-questions` 的 `types.ts`）。
- 审批通道另有一个公开展示字段 `ApprovalRequestEvent.displayReason`；本插件当前仍只传 `reason`，本决定不改变审批通道的展示路径。
- 客户端 `ctx.locale.resolveText()` 按当前语言的 fallback 链解析本地化文本，键为小写且缺省回退 `en`（`@deepseek-ai/dsh-client-locale`）。
- `conversation.approval.card` 是公开 Factory，入参 `ApprovalCardInput`（`title`/`description`/`allowLabel`/`onAllow`/`onReject` 等）；`allowLabel` 覆盖允许按钮标签（本插件取 `intent.display.approve`），「拒绝」等固定操作由 approval 语言包本地化（`@deepseek-ai/dsh-client-ui-approval`）。
- `PostToolDecision.additionalContexts?: UserMessage[]` 是公开契约（`@deepseek-ai/dsh-tools` 的 `contracts.ts`）；`UserMessage` 形状为 `{ role: 'user', id, content, source }`，`notice` 形态要求 `summary`（`@deepseek-ai/dsh-llm` 的 `message.ts`）。
- 首方 `dsh-cua` 的 `selectApplicationApproval`/`ApplicationApproval` 与 composer 链注册方式可作同款参照（`@deepseek-ai/dsh-cua` 的 `src/client/ApplicationApproval.tsx`、`mount.ts`）。

插件侧实现点（本仓库）：`src/client/settings.js` 的 `selectGuardrailsApproval`（只接管本插件问题 id）与 `GuardrailsApproval`（共享工厂优先、无工厂时最小卡片）；`src/adapter/dsh-gate.js` 的 `askViaQuestions`（写 `intent.display`）、`confirmationNotice` 与 `tools/post-execute` 监听（注入 `additionalContexts`）。

**待实测（本轮没有实测证据，不得写成已验证）**：

- 真实卡片外观需刷新页面目视：标题/说明/「拒绝」「允许一次」是否与标准审批卡一致，旧提问卡不再出现；
- 真实 GUI 中确认通知与卡片联动：下一步 user 消息可见，`rule`/`scope`/`channel`/`policy`/`reusable=no` 完整；
- 中文/英文界面切换后的按钮与 chrome 文案；
- 非 Web 客户端降级卡的实际外观与可操作性。
