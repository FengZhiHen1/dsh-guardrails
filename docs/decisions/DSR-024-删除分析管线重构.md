# DSR-024 删除分析管线重构：单一决策点与类型化 IR

- 状态：已采纳
- 日期：2026-11-17
- 关联：[需求](../需求.md)、DSR-019/020/021（策略不变）、DSR-022/023、[架构重构设计](../technical-details/架构重构设计.md)

**决定 / 理由 / 被否决项：** 重建删除分析内部架构为「前门分类 → 类型化命令 IR → 删除 sink 识别 → 证据适配器 → **单一策略决策点**」；策略层 `deny` 以「存在删除 sink 证据」为前提，无 sink 命令直接放行。否决「沿用命令族授权（白名单式只读命令 + 选项白名单）」与「增量打补丁修误报」。

## 背景

三路只读审计与本会话实测表明：坏的不是产品策略，而是实现偏离了它自己确认的架构。

- 解析层把 AST 压平成 `{name, args: string[]}`（`powershell-helper.ps1:146-158`），丢失「引号字面量 vs 参数标志」；core 用 `/^-{1,2}/` 正则重猜选项（`deletion-intent.js:581`），对「已知只读命令 + 不认识的选项」直接拒绝。本会话复现：`Write-Output '--- label ---'`、`Get-ChildItem -Include`、只读 `foreach` 循环、`git clone $var` 全部被误拒；历史 DSR-021 就是为收敛同类过度防御而设，一个版本后同类又从新入口长回。
- 允许/拒绝极性反转：未建模程序（`Test-Path`/`whoami`）按当时 L3 放行，而知名只读命令换个选项被拒——越了解一个命令越容易被拦，与当时的定位「只防灾难性删除」矛盾。
- 结构重复：灾难身份（当时称 L1）在 `policy.js`（ABS-*）与 `deletion-plan.js`（DEL-12/13）两处算；命令→操作文法两套；文件系统遍历两套、单调用最多盘三遍；保护匹配、路径包含各多份且大小写语义不一致；删除分档阈值判定落在 adapter，违反「领域逻辑在 core、可裸 Node 测」。
- 失败语义不一致：文档称判定异常 fail-open，代码 fail-closed；未知配置键导致插件整体不挂载、守卫与打码一起静默消失。

## 真实方向与评价

| 方向 | 评价 |
|---|---|
| 沿用「命令族授权」并打补丁：补选项白名单、修 dash 字面量、扩大只读命令集 | 治标；仍保留「证明命令只读才放行」的反转极性与无限白名单维护；每加命令/选项即复发 |
| 清室重写（新 core，只迁移证据模块，删旧路径） | 概念最干净，但一次性风险与验证面最大 |
| **按现有分层的定向重构**：保留 adapter/core 分层与可复用证据模块，重写 IR 边界与决策归属（选定） | 既消除根因，又复用已验证的证据适配器与测试；迁移风险可控 |

选定向重构而非清室：证据模块（git/mount/disposable/身份）是干净且经测试的好代码，清室重写会丢弃它们；而 IR 边界与决策归属是真正坏掉的部分，定向替换即可。

## 决定

1. **类型化命令 IR**：解析层产 `ArgElement[]`，保留 `role(parameter|operand)` 与 `value.kind(literal|variable|substitution|glob|unknown)`；core 不再用正则把字符串重猜成选项。
2. **删除相关性门控**：`deny` 需先有删除 sink 证据；无 sink 命令（含只读查询的未知选项、循环、成员访问）直接放行。
3. **单一策略决策点** `core/policy.decide(evidence)`：独占灾难身份判定、删除分档阈值算术、敏感文件命中、语言层动态目标转确认；不 import adapter、可裸 Node 测。
4. **证据适配器统一**：一套 walker、一套路径包含（单一大小写语义）、一套受保护匹配。
5. **统一失败语义**：配置坏降级不卸载；解析失败按「是否含删除候选」分流；内部异常 fail-closed。
6. **数据/执行区分**：仅在可执行位置识别删除 sink；`grep "rm -rf"`、提交信息中的删除字样不误拦。

## 重访条件

若定向重构过程中发现证据模块与新 IR 边界耦合比预期深，重访是否清室重写证据层；若类型化 IR 的两方言映射成本超预算，重访是否先只改 PowerShell（误报主源）再推 Bash。任一情况以实测证据触发。
