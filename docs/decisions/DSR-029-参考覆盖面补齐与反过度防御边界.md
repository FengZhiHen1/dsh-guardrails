# DSR-029 参考覆盖面补齐与反过度防御边界

## 背景

对照两个成熟项目的防御面清点本插件的覆盖：CC Safety Net 的 74 条破坏性命令规则，以及 Destructive Command Guard 的 28 个 pack 类别、1198 条 pattern。结论是本插件在若干具体形态上不可见（删除族、包装器、`cmd.exe`、git 子命令、程序字面量、部分凭据位置），而在已建模形态上更严格（目标不可枚举默认确认、批量按证据计数）。

同一时期确认了两类相反的风险：一是覆盖缺口被当成拒绝理由，二是缺口本身静默放行却不留可核对范围。前者违反「默认放行、低误报优先」的定位，后者使防护不可解释。

## 决定

1. **只补同一威胁模型内的可识别形态**，不引入参考项目的默认拒绝策略：`find -delete`/`-exec rm`、`xargs`/`parallel` 加字面删除 argv、`shred`、`rsync --delete`、透明包装器（`sudo`/`env`/`nice`/`time`/`stdbuf`/`nohup`/`command`/`exec`/`timeout`）、`cmd /c` 薄方言、git 工作树状态丢弃类、解释器程序中的字面量 shell 串与 `require(...)` 直连链、词首 `~` 归一，以及云/数据库/K8s 每类最高危的少数删除子命令。
2. **不新增规则号**。新增形态全部映射既有契约目录：删除族与远端删除进入 `data.delete.*`，git 状态丢弃进入 `data.git.restore`，凭据位置进入 `credential.file.read`/`.mutate`。
3. **非宿主执行域与远端删除不落本地盘存**。表达为 `delete` 加 `unknown` 目标与 `knownScope`（域或命令范围），可附带 `details.remote`；判定为 `data.delete.dynamic` 确认。云、数据库、K8s 一律确认档，不得拒绝。
4. **反过度防御为判定不变量**：
   - 覆盖缺口（`unmodeled-command`、`no-provider`、`cmd-inline`、`wsl-shell`、`interpreter-options` 等）单独存在时放行并留诊断；只有分析故障与盘存出错走拒绝。
   - 只认破坏性动作本身：命令名、未知选项、参数存在不产生判定；只读子命令与 `--dry-run`/`--help`/`--version` 无操作、无候选。
   - 包装器解包只重发内层命令事实，内层程序动态时记缺口放行，不凭外层升级。
   - git 只补真正不可逆形态：`branch -d`、`checkout <branch>`、`checkout -b`、`switch <branch>` 放行。
   - 每个新增形态带正常用法反例，作为放行回归门禁。
5. **凭据只按精确尾段组合扩展**（如 `.kube/config`、`.docker/config.json`、`.config/gh/hosts.yml`、gcloud 凭据文件、`.azure/accessTokens.json`）与高置信 basename；不按扩展名或目录段整类拦截。

## 取舍

- **不做**云/数据库/容器/系统的全量逐命令矩阵、Secret Manager 厂商子命令、`ssh` 与容器运行时的载荷解包、`Get-ChildItem | Remove-Item` 一类无显式路径的管道删除、`git rebase --abort`/`merge --abort`（需进行中状态的只读探测）、`cmd.exe` 的 `for`/`if`/`%VAR%` 与 `/k` 形态、解释器脚本文件正文（DSR-028 不变）。
- **保留**参考项目在「未建模即拒绝」上的差异：本插件对未建模形态放行，代价是覆盖面小于 DCG 的 pack 全量，收益是低误报与可解释的缺口。
- **代价**：`shred` 一律按删除分档；`rsync --delete` 与 `find -delete` 在目标为空时可能放行、在批量时确认，二者都以实际盘存为准，不声称精确总数。

## 后果

- 防御面增量集中在不可逆数据破坏与凭据读取，判定仍保持「拒绝 > 确认 > 放行」与默认放行。
- 正常用法回归成为持续门禁：`git status`、`checkout -b`、`switch`、`branch -d`、无 `-delete` 的 `find`、无 `--delete` 的 `rsync`、`kubectl get`、`aws s3 ls`、`psql -c "SELECT 1"`、`docker ps`、`wsl ls`、`sudo ls` 等必须放行且无候选。
- 部署侧若仍运行不读取脚本正文之前的构建，会出现与本决策相反的误拦；版本核对与部署验证由部署流程负责，不属本决策。
