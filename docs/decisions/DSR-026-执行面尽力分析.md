# DSR-026 执行面尽力分析（取代 run_code 一律拒绝）

- 状态：已采纳
- 日期：2026-11-17
- 关联：[需求](../需求.md) R-13/R-17、[规则模型](../technical-details/规则模型.md)、[跨语言删除分析](../technical-details/跨语言删除分析.md)、DSR-019/020（`run_code` 条款被取代）、DSR-025（三档判定）

**决定 / 理由 / 被否决项：** 执行面（`run_code`/PTC 程序、语言运行时脚本、内联代码、shell 动态执行）由"一律拒绝或无条件放行"改为"**先尽力静态分析**：识别删除 sink 并按删除分档处置；无法分析且含删除候选 → 确认；无删除候选 → 放行"。否决"一律拒绝"与"无条件放行"。

## 背景

用户指出：`run_code` 是 PTC 模式工具，希望**尽力分析**而非直接拒绝；语言运行时脚本需要**识别对应脚本再分析**，不是无条件放行。核对 DSH 基线（`knowledge/v0.2.0-rc.2/agent/11-tools.md:93-107`）：

- PTC 模式下模型只能直呼 `run_code`，其余工具折叠为 `UNKNOWN_TOOL`；`run_code` 载荷是 **TypeScript 或 Python 源码**（`ctx.ptcRuntime.language`）。
- `tools.<name>` SDK 子调用在派发时**另走完整流水线**（各自审批与守卫）。
- 旧实现对 `run_code` 与所有语言运行时一律拒绝/放行，既浪费了可分析性，也与"安全网"定位不符。

## 真实方向与评价

| 方向 | 评价 |
|---|---|
| 维持一律拒绝（DSR-019） | 把可分析的 TS/Python 源码也拒；`run_code` 是 PTC 唯一入口，等于 PTC 模式不可用；弃 |
| 无条件放行语言运行时 | 保留 `python cleanup.py` 盲区，与"识别脚本再分析"要求相反；弃 |
| **尽力分析 + 三档**（选定） | 用 TS/Python provider 分析 `run_code` 与脚本、内联源；不可分析含删除候选转确认、无候选放行；兼顾安全与可用 |

## 决定

1. **`run_code`（PTC）**：按 `ctx.ptcRuntime.language`（TS/Python）分析其程序源码的直接删除 sink，按删除分档处置；`tools.<name>` 子调用另走守卫。
2. **语言运行时脚本**：识别脚本入口（`python`/`node`/`tsx`/`deno`/`bun`/`uv`/`npm|pnpm|yarn run`），交 provider 分析；**不再不透明放行**。
3. **内联代码**（`-c`/`-e`）：分析内联源，不再按 `DI-INLINE-CODE` 整体拒绝。
4. **无 provider 的运行时**（ruby/perl/php 等）：识别脚本后转**确认**（已识别未建模），不放行。
5. **不可分析的执行**：含删除候选 → 确认；无删除候选 → 放行；命中灾难身份 → 拒绝。
6. **取代** DSR-019 第 3 条"`run_code` 一律拒绝"与 DSR-020 中 `run_code` 仍拒的表述。

## 直接后果

- `需求.md` R-13/R-17、判定表执行面一行、`规则模型.md` execution 规则、`架构重构设计.md` 决策点第 6 档、`跨语言删除分析.md` 入口识别与失败语义同步改写。
- 相对旧实现的可见行为：`run_code` 由拒绝 → 分析后分档；`python x.py`/`node x.js` 由放行 → 分析；`node -e`/`python -c` 由拒绝 → 分析。
- `execution.dynamic-command`（`& $cmd`/`iex` 等动态命令名）无法分析 → 确认。

## 重访条件

若对 `run_code` 的静态分析在生产中误报/漏报不可接受，或 PTC 运行时语言扩展超出 TS/Python，重访分析深度与 provider 覆盖。若"不可分析→确认"在高频纯计算 `run_code` 上噪声过大，重访是否允许"无删除候选即放行"的启发式更激进。
