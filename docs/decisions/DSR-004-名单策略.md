# DSR-004：名单策略——硬编码 + 布尔开关

## 上下文

规则类别各有 config 布尔开关（env/git/credentials/sessions/destructive，范围 B 增加 system）。敏感名单（文件名/后缀/目录段/组合）是否配置化是一个设计分叉。

## 真实方向与评价

- 硬编码：名单随代码版本交付，改动走代码评审与测试。与仓库规则一致（AGENTS.md：不添加推测性灵活性）；安全名单属于"默认拒绝"语义，配置化会把策略负担与误配风险转嫁给用户。
- 配置化名单（config 中声明额外敏感路径）：灵活，但引入名单格式、合并语义、错误处理与文档成本；v1 唯一用户是本机两个 profile，没有跨机器配置需求。

评价：配置化在当前需求下是推测性灵活性；布尔开关已覆盖"某类别整体关闭"的真实需求（如 test 环境调试）。

## 最终决定

名单硬编码 + 类别布尔开关；不提供自定义名单配置。

## 直接后果

- 新增敏感目标通过代码变更 + 测试用例交付。
- 需求.md 的 C-04 固化该约束。

## 重访条件

- 出现跨机器分发且各机器名单不同的真实需求时。

## 重访记录（2026-08，DSR-006）

开关结构由"类别布尔"扩展为**叶子级防御层配置**（v2：类别键布尔/对象、`destructive` 六子族、`unverifiable` 键），见 [DSR-006](DSR-006-防御层全量配置化.md)。本决策反对的**名单配置化**（config 声明自定义敏感路径）仍然维持不变；"布尔开关已覆盖真实需求"的当时结论被 DSR-006 的新需求（细分防御层、消除 destructive 误伤）替代。
