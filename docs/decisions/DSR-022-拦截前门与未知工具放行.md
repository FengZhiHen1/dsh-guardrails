# DSR-022 拦截前门与未知工具放行

- 状态：已采纳
- 日期：2026-11-17
- 关联：[需求](../需求.md) R-16、[架构重构设计](../technical-details/架构重构设计.md)

**决定 / 理由 / 被否决项：** 把删除分析的适用范围收敛到**命令执行面**（`bash`/`pwsh`/`py`/`node` 命令、`terminal_send` 文本）与**结构化文件工具的删除或移动目标操作**（不解析命令文本，但计入删除分档），MCP 与未知工具一律放行、不再默认拒绝。否决「未知工具默认拒绝」。

## 背景

旧实现 `host.js:268-275` 对不在 `isAnalysedTool` 也不在 `FRAMEWORK_SAFE_TOOLS` 的工具返回 `[UNKNOWN_TOOL]` 默认拒绝。`FRAMEWORK_SAFE_TOOLS` 是一张写死的 DSH 内置工具白名单（`host.js:160-174`），MCP 工具不在其中，于是一个图像/检索类 MCP 工具也被当成「可能有删除副作用」拒绝。用户实测指出该行为过宽。这与本插件当时的定位「只防灾难性删除」直接冲突：非命令工具不具备删除宿主文件的能力。

## 真实方向与评价

| 方向 | 评价 |
|---|---|
| 维持「未知工具默认拒绝」 | 与「只防灾难性删除」冲突；MCP 等无删除能力工具被误拦；每新增工具都要进白名单 |
| 未知工具全放行、但对其 payload 仍做敏感路径扫描（CCSN 的「unknown 路由」） | 更稳妥，但把「删除」和「敏感文件」两件事混在未知工具上；实现复杂、收益低 |
| **只对命令执行面做删除分析，其余放行**（选定） | 与产品定位和用户指令一致；消除 MCP 误拦；范围清晰可证 |

## 决定

1. **命令执行面**：`bash`、`pwsh`、`py`/`node` 等语言运行器入口、`terminal_send` 命令文本 → 进入删除分析。
2. **结构化文件工具**（`read`/`write`/`edit`/`delete`/`move`）→ 不经 shell 解析；其删除或移动目标操作进入同一删除分档，并做敏感文件与灾难身份判定。不解析命令文本不等于不计数。
3. **其余一切工具**（MCP、未知工具、网络、编排、问答、`workflow` 等）→ **放行**，删除分析不介入。
4. 删除 `[UNKNOWN_TOOL]` 默认拒绝路径。

## 直接后果

- `需求.md` 新增 R-16；`规则模型.md`「默认拒绝未审查工具」相应收敛为「非命令工具放行」。
- `host.js` 前门分类改写；`FRAMEWORK_SAFE_TOOLS` 白名单不再承担安全语义。
- 覆盖边界显式化：一个经 MCP 暴露的文件系统工具若删除文件，删除分析**看不到**——这是已接受的范围边界，不再用「未知工具默认拒绝」补救。

## 重访条件

若出现经 MCP/未知工具造成真实删除事故的证据，重新评估是否对未知工具的**显式文件参数**做最小敏感路径扫描；届时以真实事故证据为触发，而非预防性收紧。
