# dsh-guardrails 部署与安装

本文说明交付形态、平台与运行时要求、通用安装步骤、配置键与发布前置验证门禁。它面向任何使用 DSH 的读者，不包含任何特定环境的主机名、路径或运维记录。

## 交付形态

插件按 DSH 官方 Bundle 范式交付：

- 包声明 `dsh.bundle.patch`，随包携带 `cordis.patch.yml` 安装层，其中 `insert` 一行 `{ id: guardrails, name: dsh-guardrails }`。该行**不带 config**：默认值属于插件 config boundary（导出的 Schemastery `Config` schema 的 `.default()`）。
- 支持三种引入方式：
  - **registry 包**：`dsh plugin add dsh-guardrails`（从 npm registry 安装已发布版本）。
  - **`github:` 依赖**：`dsh plugin add github:<owner>/<repo>#<ref>`（钉 commit/ref 的 git 依赖）。
  - **bundle 行**：在 profile 的 `cordis.patch.yml` 中按 `id: guardrails` 引用；安装层已插入该行，用户覆盖按 id 合并，不重复 insert。
- `index.js` 为包根薄转发（`export * from src/adapter/host.js`）。适配层 `src/adapter/host.js` 以官方插件形态导出 `name` / `inject` / `Config` / `apply(ctx, config)`（无 default export），注册 `ctx.tools.guard` 钩子。
- 浏览器半侧由 `dsh.client`（platform web）声明，`exports["./client"]` 指向惰性 CJS bundle，向 `plugins.row.config` 注册本行配置页。

## 平台与运行时要求

- **Node**：按包 `engines.node` 声明（`^22.19.0 || >=24`）。
- **DSH 版本区间**：`engines.dsh` 与 `@deepseek-ai/dsh-settings` peer 同为 `>=0.2.1-rc.2 <0.3.0-0`。当前验证基线为 `0.2.2-rc.2`；更低版本会被 peer 门禁禁用（整行不加载），不静默降级。
- **Shell 解析依赖**：
  - PowerShell 使用微软官方 `Parser.ParseInput`，通过持久 `pwsh` helper 提供事实；可信 `pwsh` 是 PowerShell Provider 的运行依赖。
  - Bash 使用固定的本地官方 `shfmt v3.12.0` typed JSON AST；交付二进制目标为 Windows x64、Linux x64/arm64，附来源、SHA256 与许可信息。解析调用不在线下载、不要求安装 Go。
- 交付目标是上列平台与版本；各平台的真实运行证据不归本文拥有。

## 通用安装步骤

1. **确认目标运行时版本**满足上面的 DSH 版本区间。
2. **安装插件行**：`dsh plugin add <spec>`，其中 `<spec>` 为 registry 包名、`github:owner/repo#ref` 或 `link:<源码目录>`（仅用于隔离试验，见下）。
3. **核对安装结果**：用 `--dump-config` 复查该 profile，确认恰好一行 `id: guardrails / name: dsh-guardrails`、来源正确、无 `disabled`、无重复行。
4. **配置（可选）**：在 profile 的 `cordis.patch.yml` 中按 `id: guardrails` 覆盖配置键（见下节）；不改安装行本身。

`link:` 源码直挂只用于隔离试验环境；发布与稳定环境应使用 registry 包或 `github:` 钉 ref 依赖，禁止源码路径直挂。

## 配置键

**本节描述当前实现的配置键。** 目标配置模型是配置 A（per-rule 规则级配置），不归本文拥有，见[规则模型](规则模型.md)「配置模型」节。

以下配置经 schema 与测试验证：

| 字段 | 默认 | 含义 |
|---|---|---|
| `sensitiveFiles` | `[]` | Profile 中的精确绝对文件路径；不接受相对路径或通配符，不是目录保护名单 |
| `builtinSensitiveAsk` | `true` | 内置敏感文件名单（私钥、工具凭据文件、系统凭据库、分页与休眠文件）的内容操作确认开关 |
| `askTimeoutMs` | `120000` | 本插件自有确认的等待上限（毫秒）；legacy `0` 映射为 `120000`，不再无限等待 |

确认只接受本次通过；拒绝、取消、超时、不可用、异常或会话 `never` 均不执行。超时只约束本插件主动发起的确认，不修改全局 DSH 确认机制。确认语义见[规则模型](规则模型.md)「确认语义」节；删除分档阈值与可重建豁免分别归[需求](../需求.md) R-07 与[可重建豁免](批量删除白名单.md)，本文不复述。

配置页面使用官方 `plugins.row.config` 入口，通过 `ctx.configForms` 读写活值；字段与保存键按官方 `SettingsForm`/`fields` 的几何复制，未修改或输入非法时禁用保存，只用主题 token，不引用 Harness Client 包。

## 发布前置验证门禁

发布或更新稳定环境前，应通过以下通用判据：

1. **源码与测试全绿**：`node verify/run-verify.mjs`（源码语法 + 测试）；如设 `DSH_RUNTIME_PATH` 指向现场运行时，可同时执行真实 ToolRuntime/ApprovalService/PTC bridge 测试。测试数量与 skip 构成以当次输出为准。
2. **组合断言**：目标 profile 的 `--dump-config` 恰一行 guardrails、无重复行、无源码解析残留，依赖为发布物形态（registry 版本或 `github:` 钉 ref）。
3. **启动无静默禁用**：实例启动期无 `N entries did not activate` / `startup failed` / `disabling profile plugin`；行确实达到 ACTIVE。
4. **功能冒烟**：用合成目标实测三类动作。可识别删除照常计数并按删除分档处置——可重建批量清理放行、普通少量删除放行、批量与不可枚举目标确认并列范围，灾难身份拒绝。受保护文件的内容操作触发确认。执行面按目标策略验证：可识别的删除按分档处置，含删除候选但无法判定则确认，无删除候选则放行。MCP 等非命令工具放行。危险命令只用模拟或隔离 fixture。
5. **跨平台**：Linux x64/arm64 实跑与性能分位数；文件存在或打包成功不代表平台已运行通过。

门禁结果是发布的前提，源码测试通过不等于部署完成。启动真实实例做冒烟属现场操作，须在具备授权与隔离条件的环境中进行，并单独记录失败、skip 与覆盖限制。
