# dsh-guardrails 部署

## 权威范围

本文唯一拥有 `dsh-guardrails` 的包形态、部署红线、安装与验证命令、生效流程、测试体系与发布路径。需求归 `../需求.md`，规则机制归 `规则模型.md` 与 `命令文本分析.md`。

## 结论先行

按 DSH 官方 Bundle 范式交付：包内声明 `dsh.bundle.patch` 并携带 `cordis.patch.yml` 安装层，profile 用官方 CLI（`dsh plugin add`）安装并自动对账 `dsh.profile.bundles`。部署红线（AGENTS.md）：**test 源码直挂，web 只吃发布包**；任一 profile 禁止 bundle 层与用户 patch 层重复 insert 同一行。

> ⚠️ **代际更正（v1.6.0，2026-09-27）**：旧文写「重复 id 导致整个 profile 启动失败（`duplicate loader entry id`）」——该守卫**已被上游 revert 删除**（`dsh-v0.1.7-rc.2` 源码 0 命中，提交 `e07f41d5fd`），重复 id 现改为**静默后者胜出**。⇒ 重复行**不能再靠报错发现**，只能人工核对各层行清单（且须按层级判定，全文 id 计数会大量假红，见知识库 `must-read/05` §6.1）。

## 包形态

`plugins/dsh-guardrails/`（仓库内唯一源码，submodule）：

- `package.json`：`name: dsh-guardrails`，`dsh.bundle.patch: ./cordis.patch.yml`，`dsh.client`（platform web，inject `@deepseek-ai/dsh-client-ui-primitives` / `@deepseek-ai/dsh-client-ui-settings` / `@deepseek-ai/dsh-client-ui-plugin-manager`），`exports["./client"] → ./src/client/card.js`，`files: [index.js, src/, cordis.patch.yml]`，`engines.node: ^22.19.0 || >=24`；核心包**一律不写 `dependencies`**（v1.4.0 起，此前 `@deepseek-ai/schemastery` 曾挂在 deps，会在 profile 落一份冗余物理副本）：`peerDependencies` 声明 `@deepseek-ai/cordis` + `@deepseek-ai/dsh-settings` + `@deepseek-ai/schemastery`，其中装载期真正 import 的 `schemastery` 另列同版本 `devDependencies`（`src/adapter/host.js` 需要，裸 node 单测才能解析；profile 侧因自身 `autoInstallPeers: false` 不会装回）。前两者不在装载期 import，故无需 devDeps。危险等级分类见知识库 `04` §7。
  - **v1.6.0 起 peer 范围必须覆盖目标运行时**（`cordis ^4.0.4` / `dsh-settings ^0.1.7-rc.2` / `schemastery ^3.18.4`）：`dsh-v0.1.7-rc.2` 新增 **peer 版本不兼容门禁**——`@deepseek-ai/dsh*` peer 范围不满足运行中的 DSH 版本时，**整行被自动改成 `disabled: true`、插件根本不加载**，实例照常启动、只在 stderr 留一行 `dsh: disabling profile plugin …`（最高危的静默变哑）。判定用 `semver.satisfies(rt, range, { includePrerelease: true })`，手工复核**必须带该选项**否则整列判错（知识库 `must-read/05` §7.2/§7.2.1）。
  - `devDependencies` 的 schemastery 必须与 peer 同代（`^3.18.4`）：`volatile()` 在 3.18.2 **不存在**（实测 0 命中，3.18.4 为 28 处），旧版会让 `Config` 在 import 期直接抛错。
- `cordis.patch.yml`：随包分发的安装层，`insert` 一行 `{ id: guardrails, name: dsh-guardrails }`——**行不带 config**：默认值属于插件 config boundary（导出的 Schemastery `Config` schema 的 `.default()`，DSH 官方范式，见 DSR-006/规则模型.md 配置模型）；用户覆盖在该行基础上按 `id: guardrails` 合并。行 `name` 与包名一致供 Node 模块解析，行 `id` 是稳定身份供 profile 层覆盖，**同时就是 settings 命名空间**（见下条）。
- `index.js`：包根薄转发（`export * from src/adapter/host.js`）。适配层 `src/adapter/host.js` 是官方插件形态——具名导出 `name` / `inject` / `Config` / `apply(ctx, config)`（无 default export），注册 `ctx.tools.guard` 钩子；settings 接线为 **v0.1.7「profile 条目 Config + `.volatile()` + 操作时读值」模型**（v1.6.0 起）：六个字段全部 `.volatile()`，`apply` 内用 `settings.configure({ auto: false }, ctx.fiber)` 声明自绘页面，guard 在**每次判定时**读 volatile 引用（`ref.get()`）——设置页写入即热生效，无需重挂载、无 `onChange` 回调。
- `src/client/card.js`：浏览器半侧（`dsh.client` 声明，`exports["./client"]` 直指）——DSH client 模块系统的惰性 CJS bundle，向 **`plugins.row.config`** 注册本行配置页（key = `dsh-guardrails#guardrails`），经 `ctx.configForms.get('guardrails')` 读写、`configForms.whileServed([...])` 仅在 Host 提供该命名空间时挂载（v1.6.0 起；旧的 `settingsScope` + `settings.plugin.item` 在新基线**零命中**）。
- `src/core/`：功能层六模块（纯领域逻辑，禁 `@deepseek-ai/*` import，仓库分层门禁强制）；目录与职责详表见 `工程结构与测试体系.md`。
- `test/`（`*.test.mjs`）：规则矩阵、命令解析、生命周期、settings seam 与基准目录（DSR-007）测试。

## settings 命名空间与配置生效（v1.6.0 重写）

- **命名空间 = loader 条目 id**，即 `guardrails`（不是包名 `dsh-guardrails`）：v0.1.7 取消了插件自选 kebab-case 命名空间与 `NAMESPACE_PATTERN`。Host 半侧导出 `SETTINGS_NS = 'guardrails'`，浏览器半侧绑定同一值；**在 profile 里给该行改名会一并移动命名空间并使卡片脱钩**。
- **只有 `.volatile()` 字段可写**：非 volatile 路径的写入**直接 throw**（`Config field "x" is not volatile`），且该字段不会出现在任何设置页（`volatileForm()` 只保留 volatile 子树）。
- **持久化目标是本 profile 的 `cordis.patch.yml`**（不再是 `$DSH_HOME/settings.yaml`；`settings-file` 提供方与 `settings.yaml` 已删除，settings 服务仅枚举并生成表单）。
- **设置优先级与旧代相反**：home patch 与命令行 overlay **高于**已存的表单写入；表单写入若会被遮蔽，在持久化前被拒绝。

## 部署红线（AGENTS.md 固化）

- **web（稳定）profile**：绝对拒绝源码直挂——插件只能来自已发布 npm 包（registry 版本）或 `github:` git 依赖。禁止 `link:`/`file:` 指向源码、junction/symlink 指向源码、patch 层用源码路径引用插件行。流程：修改插件 → test 实测 → 打包发布 / push → `dsh plugin --profile web add <已发布包或 github:owner/repo>`。
- **test（试验）profile**：允许源码直挂（`link:` 依赖，符号链接实时可见），用于快速验证；源码改动重启即生效。
- **任一 profile**：同一插件禁止在 bundle 层与用户 patch 层重复 insert。覆盖 bundle 行配置用 id-targeted override，不再 insert。⚠️ 重复 id **不再报错**（静默后者胜出），必须人工核对；核对**必须按层级判定**（知识库 `must-read/05` §6.1）。

## 安装与验证

CLI 一律用**实例版本二进制**（AGENTS.md 跨代红线）：`node tools/dsh-launcher-cli/cli.mjs env --json` 现查 `instances[].version_bin`（下文 `$DSH_BIN`）；实例 HOME 现查 `instances[].home`（test 实例与 stable-dev 实例分属不同 HOME，校验时以 `DSH_HOME=<对应 home>` 前缀调用）。

```sh
# test：源码直挂（link: 依赖 + bundles 自动对账；在 test 实例 HOME 下执行）
$env:DSH_HOME='<test 实例 home>'; node $DSH_BIN plugin --profile test add E:/Project/DSH_Plugins/plugins/dsh-guardrails

# 部署后必查（AGENTS.md）：无重复插件行、无源码解析残留
$env:DSH_HOME='<test 实例 home>'; node $DSH_BIN --profile test --dump-config
$env:DSH_HOME='<stable-dev 实例 home>'; node $DSH_BIN --profile web --dump-config
```

预期结果：test 与 web 的 dump 各出现 `# == dsh-guardrails` 层且恰一行 `id: guardrails / name: dsh-guardrails`，解析自 `dsh-guardrails` 包；web 依赖为发布物形态（当前 `github:` git 依赖，lockfile 承载 resolution；发布后切换 registry）。test 的 `node_modules/dsh-guardrails` 为符号链接指向仓库。

## 生效流程

- test：编辑源码 → 重启 test profile 即加载（符号链接直挂，无需重装）。
- web：当前以 `github:` git 依赖挂载（源码仓库 `FengZhiHen1/dsh-guardrails`，pnpm 克隆进 store 的只读快照，lockfile 的 resolution 钉 commit）；源码更新须先 push 到该仓库再重新 add（推荐钉新 commit ref）；发布后切换 `dsh plugin --profile web add <registry 版本>`。**v1.7.0 的具体升级命令见下节。**

## 版本基线（v1.6.0 起）

本插件适配 **DSH `0.1.7-rc.2` 及以后**（源码基线 `dsh-v0.1.7-rc.2` / 477b4f42）；**不兼容 `0.1.2-rc.1` 及更早运行时**（已按方案 B 单轨适配）。

⚠️ **在旧运行时上插件整行不加载，而非"只是少了配置页"**——实测（本机两版部署树对比）：`Config` 在**模块 import 期**即调用 `.volatile()`，而 0.1.2-rc.1 携带的 schemastery 3.18.2 **没有该方法**（`typeof === 'undefined'`，调用抛 `TypeError: s.volatile is not a function`）。⇒ 旧实例上该行会加载失败，**硬拦截失效**；这不是可接受的中间态，升级顺序应为**先升实例、后挂 v1.6.0**。

判定依据（均为本机机械取证）：
- `installSection` 仅存在于 0.1.2-rc.1 的 `dsh-settings`（`lib/index.js:327`），0.1.7-rc.2 只有 `SettingsForms`（`lib/index.js:322`，导出 `SettingsForms as default`）；
- `settingsScope` / `settings.plugin.item` 仅存在于旧版客户端；0.1.7-rc.2 客户端为 `configForms` / `plugins.item`（各自零命中对方）；
- `volatile()` 在 0.1.2-rc.1 的 schemastery 中 **0 命中**，3.18.4 为 **28 处**；
- `.volatile()` 在旧版上调用即抛 `TypeError`（已实跑复现）。

⇒ **升级顺序（硬性）**：先把 target 实例升到 `0.1.7-rc.2`，再挂载/更新 v1.6.0。反向操作会静默失去硬拦截。

## 发布路径（web 启用前置步骤）

发布前置门禁（AGENTS.md 硬性）：**先过 test 实测**（`verify/run-verify.mjs` 全绿 + test profile 启动与功能冒烟），实测结果记入提交说明。

⚠️ **分工**：脚本第 4 步（test profile 启动冒烟）会 spawn 一个真实实例，**只能由用户在启动器侧执行**；agent 侧一律置 `DSH_VERIFY_SKIP_BOOT_SMOKE=1` 跑其余步骤（跳过会单独计数、不会冒充全绿）。故"run-verify 全绿"在 agent 侧的正确表述是"**除第 4 步外全绿，第 4 步待用户补做**"——发布前两半都要有，缺一不算过门禁。

1. `npm publish`（或 `pnpm pack` 交付 tarball；本包无 `private` 标记）。
2. `dsh plugin --profile web add dsh-guardrails`（registry 版本，替换 `github:` 依赖）。
3. `--dump-config` 复查恰一行。

> ⚠️ **v1.7.0 当前不满足本门禁的"test 实测"一半**（2026-09-29）：用户明确指示跳过 v1.7.0 的功能冒烟（"程序性的应该没问题"），且 test 实测场已按指令清空 ⇒ 实例级启动/功能冒烟**未做**。已完成的 agent 侧等效项：单测 155/155、行覆盖 98.55%、分层门禁、`npm run check` 退出 0、`quality_floor` 通过、性能与消融验证、以及对**已挂载模块**的离线判定断言（7/7）。⇒ **若要 `npm publish`，须先重建 test 实测场并补做实例级冒烟**；仅挂 web 走 `github:` git 依赖可不等发布，但仍建议补冒烟。待办见 `../TODO.md`。
